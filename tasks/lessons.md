# Lessons

项目级教训日志（现象 → 根因 → 规则）。来源：用户/协作者对交付物的更正。

## 2026-11-25 review 报告 r1 → r2 的 6 条更正

### 1. 把本机环境问题外推成项目构建依赖（C1）

- **现象**：报告写「`.cargo/config.toml` 未被跟踪 → 新克隆的机器 / CI 上 `cargo build` 会卡死或超时」，定级 [中]。
- **根因**：把「本机全局 TUNA 索引过期」这一**环境**事实，与「仓库内存在一个未跟踪的 rsproxy 覆盖」这一**事实**拼接成了「项目依赖它」的因果链。rsproxy 并非构建必要条件，干净环境直连 crates.io 可用；`.git/info/exclude` 是本地文件，clone 不携带。
- **规则**：涉及「别的机器/别人的环境会不会坏」的结论，必须有**干净环境实测**或「因果链的每一环都可独立验证」才能写；否则降级为「本机现状」并说明仓库层的真问题在哪（此处是无 README / 无 CI）。**本地配置 != 项目依赖**。

### 2. 写了「用户观感就是卡死了」却没有任何测量（B9）

- **现象**：报告断言主线程执行会导致「界面冻结、观感卡死」，定级 [中]。
- **根因**：机制推理成立（同步命令在主线程执行），但**没有测量耗时就写了感知结论**；命令体实际只需 3–66 ms。
- **规则**：机制类缺陷必须分两层写：**结构事实**（有路径证据）与**影响断言**（有测量证据）。只有前者就只写前者，级别按结构风险定（[低-中]），不得写「已发生 X」。

### 3. 把源码推定写成「已实证恒 false」（B8）

- **现象**：报告写 `window.confirm` 在 macOS 上「永远按取消」「恒 false」，而实际只是从 wry/tauri 源码推出的结论。
- **根因**：把「在第三方源码里没找到该实现」等同于「行为已被证明」，且把上游行为直接外推到「本应用必然失效」。
- **规则**：结论必须分层标注【已实证】/【源码推定】/【未验证】。能补实验就补（本例用独立 WKWebView harness 做 A/B 对照，WebKit 层变【已实证】，应用层保持【源码推定】），补不了就写明未验证边界。**禁止把上游源码结构写成「已实证的应用行为」**。

### 4. 标识符比较想用统一规则，且条目计数与实测不符（A2）

- **现象**：初稿想把主键匹配统一成大小写不敏感；且 handoff 标题把 A2 算进「go build 失败级」。
- **根因**：标识符等价性由**方言 × 引号风格**共同决定（PG 未加引号折叠小写、PG 加引号原样、MySQL 列名不敏感），统一规则会误伤合法 DDL；条目归类则靠印象而没有逐条跑 `go build`。
- **规则**：涉及标识符/大小写/引号的判断，先确认**方言与引号语义**（sqlparser 保留 `Ident.quote_style`，可据此算归一化比较键），不要发明统一规则；给报告计数时，**每条都要有可复现的判定命令**（本例逐条跑 `go build ./...` 后确认 A2 实为 exit 0）。

### 通用规则

- **结论强度不得超过证据强度**：每条结论标注证据来源（实测 / 源码路径 / 推定），并显式列出未验证项。reviewer 的 6 条更正全部命中这一条。
- **条目数 ≠ 根因数**：报告条目必须归并到根因表（如 R1–R13），同一根因的多个防御点（生成层 vs 导出层）合并标注。
- **数字要可复算**：条数、级别分布、耗时表都要给出取得方式；写进标题的数字出错会污染后续所有引用（本例标题「5 条 go build 失败级」直到 r2 才更正）。

## 2026-11-25 review r3：专项 reviewer 返回的 3 条新发现

### 5. 自查覆盖某个文件范围时，只验证了「已知的怀疑点」

- **现象**：我把 `crates/core/src/export.rs` 整个范围自查了一遍（路径穿越、批内重复路径、I/O 失败、错误映射），写了 A14/A15；但漏掉了 rev-io 找到的软链接问题（A16，会写到用户没选的目录、覆盖目录外文件）和 TTL=0 下界（A17，Redis key 永不过期）。
- **根因**：自查是「带着已知怀疑点去验证」，不是「按威胁模型逐项过一遍」。导出/落盘类代码的固定检查清单是：路径解析（词法 / 符号链接 / 挂载点）、原子性（truncate、temp+rename、部分失败回滚）、边界值（0、空串、负数、超长）、幂等与批内一致、错误信息可定位性。我只覆盖了其中 3 项。
- **规则**：接手一个文件范围做自查前，先列出该类代码的**固定检查清单**再逐项过；写文件的代码默认要问「原内容会不会先被清掉」「路径会不会被符号链接带出目标目录」「0/空串这类边界值会不会被当成合法输入」。

### 通用规则（补充）

- **子代理的产出要自己复核，但不能因为自己复核过就当它没有增量**：rev-io 返回的 5 条与我的重合（说明我的范围覆盖是有效的），但仍有 3 条我漏了 —— 并行 reviewer 的价值正是在于用不同视角覆盖同一范围。

## 2026-11-25 review r4：修法本身也要标边界

### 6. 把「部分保证」写成了「消除问题」

- **现象**：r3 报告的 A16 修法写成「canonicalize 校验确认仍在目标目录内」，A15 修法写成「临时文件 + rename；失败时清理已写文件、内存备份回写」—— 都被 reviewer 指出越界：A16 的检查与写入之间存在 TOCTOU 窗口（且没提平台差异），A15 只提供单文件原子性（整批不是事务）、失败清理可能删掉原有文件、内存回写不保证恢复。
- **根因**：写「修法」时按**理想实现**描述，没按**当前实现能提供的保证**描述；把「检查」「单文件」「尽力而为」都写成了「解决」。
- **规则**：每条修法必须回答三问 —— (a) 保证到哪一层（单文件 / 整批 / 跨平台）？(b) 剩下的窗口或失败模式是什么（TOCTOU、跨卷 rename、磁盘满时的回写）？(c) 哪些是产品决策、要谁拍板（策略选哪条、要不要整批事务）。写不出这三问，说明还没想清楚，别写成「已解决」。

## 2026-11-25 会话语言：全程用英文回复

### 7. 忽略了全局 CLAUDE.md 的语言设置

- **现象**：本会话所有回复（包括 review 报告与提交说明）都用英文，违反全局 `~/.claude/CLAUDE.md` 的「语言设置：所有回复必须使用中文」。
- **根因**：项目 `AGENTS.md` 没有重复这条规则，我在长链路任务（多子代理 review）里只按项目文件与输出风格作答，没有在起草回复前回看全局指令文件；全局与项目指令是**叠加**关系，不是二选一。
- **规则**：每次组织回复前先确认全局语言设置；项目文件不会覆盖「回复语言」这类全局偏好。中文回复统一使用英文标点，并在中文、英文、数字之间留空格。


## 2026-11-26 发布流水线：参数分隔符只该有一个

### 8. 在 action 已经插了 `--` 的地方又加了一个 `--`

- **现象**：第一次真实跑 `release.yml` 两格都挂在 `Build and publish`，报错是 `failed to bundle project: can't open main binary target/release/gorm-generate: No such file or directory`；日志里 npm 回显的是 `> tauri build -- --target x86_64-apple-darwin`。
- **根因**：`tauri-action` 执行 `<tauriScript> <command> -- <args>`，自己插了一个 `--`；我在 `tauriScript` 里又写了 `npm run tauri --`，两个分隔符叠在一起。npm 只吃掉第一个，第二个作为字面量参数进了脚本 —— tauri CLI 的 `--` 之后是「传给 runner 的参数」，于是 `--target` 被当成 cargo 的参数，cargo 编到了 `target/x86_64-apple-darwin/`，而打包器仍按宿主 target 目录找二进制。
- **规则**：参数分隔符只能有一个，且要确认**是谁加的**。写 `npm run <script>` 形式的 action 时，不要自己再加 `--`：action 的分隔符就是给 npm 用的，npm 会把它吃掉，CLI 最终收到的是干净的 `build --target <arch>`。这类拼接**在推 tag 之前先用本地同一条命令跑一遍**（本次 `npm run tauri build -- --target …` 本地一跑就能看出来），别用 20 分钟的 CI 循环代替一次本地验证。


## 2026-11-26 改 workflow：删步骤时把下一步的缩进带坏了

### 9. 删除 workflow 步骤时，缩进多了一格

- **现象**：给 release workflow 去掉 Apple 签名步骤后，GitHub 上连续两次出现 `failure` 且 `This run likely failed because of a workflow file issue`，0 秒结束、一个 job 都没有；CI 本身是绿的。
- **根因**：删掉整段步骤时，把后面 `- name: Build and publish` 那一行多缩进了两格（12 空格而不是 6），于是它在 YAML 里不再是列表项，而是落进了上一个 `run: |` 的脚本块里当普通文本。YAML 本身仍然合法（所以本地解析器、`ruby -e 'YAML.load_file'` 全过），但 workflow 的 schema 失效：`Build and publish` 这一步不再存在，发布流程实际已经不产出了。
- **规则**：改 workflow 后不能只看 YAML 能不能解析 —— 要看**结构对不对**。最省事的检查是把改动后的文件与上一次跑通过的文件 diff，确认差异只有预期的那些行；再补一条结构断言（每个 step 是 mapping，且恰好有 `uses` 或 `run` 之一）。这次 `git diff 0497858 -- .github/workflows/release.yml` 一眼就能看出 `Build and publish` 的缩进变了。


## 2026-11-26 用户报障：PG 方言下自带样例解析不了

### 10. 方言开关只改了枚举，没管编辑器里那份脚本

- **现象**：用户在配置里把方言切到 PostgreSQL，点 Generate 得到一段 sqlparser 原始报错（`Expected: identifier, found: ` at Line: 1, Column: 14`），报错指向反引号，指向不到真正的问题 —— 方言选错了。应用自带的样例只有 MySQL 一份，且与方言下拉框毫无联动。
- **根因**：把「方言」当成只影响解析的一个枚举值，没意识到界面里存在一份**内容**必须与之一致；同时 core 的错误分类只有「解析失败」与「语义校验失败」两支，方言层面的错被压进了「解析失败」，用户拿到的诊断止步于字符级。
- **规则**：任何影响输入语义的开关，都要同时检查**应用自带的内容**是否与之一致 —— 带内容耦合的开关要带内容联动；错误分类按**根因**分，不按**现象**分：「解析失败」是现象，「方言不匹配」是根因，只有后者才告诉用户该改什么。
- **补充**：同一段 DDL 在两种方言下会生成**不同**的模型（sqlparser 只在 MySQL 方言下保留 `AUTO_INCREMENT` 列选项，PG 下这个 token 被吞掉，主键悄悄丢掉 `autoIncrement`）。所以「解析成功」不等于「语义正确」，方言相关的丢失必须显式报警。

## 2026-11-27 引入第二个测试运行器：先检查第一个会不会去捡它的文件

（来源：retro 提案，会话内 review 发现，经 maintainer 合并确认。）

### 11. 「新套件绿」不等于「门禁绿」

- **现象**：PR #20 加 `e2e/app.spec.ts`（Playwright）时，E2E 自己 4/4 绿，但 `npm test` 变成 1 failed：`Playwright Test did not expect test() to be called here`。CI 的 `frontend` job 会在单测那一步直接挂，后面的 E2E 步骤永远跑不到。
- **根因**：Vitest 默认按 `**/*.{test,spec}.*` 收集，`e2e/` 也在其中；新套件自己通过只能证明它能跑，没有证明它与既有运行器的收集边界不冲突。这个问题是推送前的会话内 `/code-review` 抓到的，离 CI 只差一次 push。
- **规则**：引入第二个测试运行器（或任何新的 `*.spec.*` / `*.test.*` 目录）时，必须跑一遍**既有运行器的完整命令**，并显式划界（本项目在 `vite.config.ts` 用 `exclude: [...configDefaults.exclude, "e2e/**"]`）。只跑新套件不能当作验证。

## 2026-11-27 抽取共享守卫：输出兼容 ≠ 把旧缺陷也搬过去

（来源：retro 提案，会话内 review 发现，经 maintainer 合并确认。）

### 12. 「行为不变」指外部输出不变，不包括不成立的防御

- **现象**：从 `SqlEditor` / `CodePreview` 抽 `useHighlight`（PR #22）时，`SqlEditor` 卸载只清了防抖计时器，`CodePreview` 则完全没有清理；两处都让已经在途的那次高亮仍会落地写回 `html`。逐字搬运会把隐患原样保留。
- **根因**：把「行为不变」理解成「每一行都照搬」，而被抽取的恰恰是防御逻辑 —— 判断标准应是这条防御**是否真的成立**，而不是它原来是否被复制了两遍。
- **规则**：重构与抽取时，逐条列出被搬移的防御性质（竞态、清理、边界值），分开判断「保留输出兼容」与「修掉不成立的守卫」；新 owner 让修复成本最低时顺手修，并补一条直接测试（本次是 `useHighlight.test.ts` 的「销毁后落地结果被丢弃」）。重构 PR 的说明里要写明哪些缺陷是继承的、哪些是顺手修的。
