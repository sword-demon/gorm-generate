# 导出先规划再写盘

## Status

accepted

## Context

`export_project` 一次做完四件事：校验路径、检查符号链接与冲突、暂存内容、持久化。其中只有前一半是纯逻辑，测试却全部要建临时目录、真的写文件才能观察到结果；路径穿越、绝对路径、重复目标这些最容易出错、也最值得穷举的判定，只能靠文件系统副作用来验证。

候选 7 要求把导出拆成「规划」与「写盘」两段。障碍是：符号链接与「目标已存在」必须读文件系统，纯函数做不到，所以规划无法承担全部判定。

## Decision

`export_project` 仍是唯一公开函数，内部实现为 `write_plan(&plan_export(dir, files)?, overwrite)`。`WritePlan`、`PlannedWrite`、`plan_export`、`write_plan` 都是 crate 私有：

- **规划**（纯）：根目录必须绝对、`safe_join` 拒绝绝对路径/`..`/`\`/`:`、重复目标检测。只产出「哪个绝对路径、写什么字节」，不碰文件系统。
- **写盘**（适配器）：符号链接拒绝（staging 前后各一次，属于 TOCTOU 缓解）、`overwrite=false` 时的冲突收集、暂存与持久化。

不引入 `FileSystem` trait。导出只有这一个适配器，换实现不是需求；拆分的价值在测试面（纯逻辑可以不带临时目录穷举），用 trait 换来的只是间接层。

## Consequences

- 路径规则的单测直接断言 plan 的错误，不建目录、不写文件；`export_project` 的集成测试保留，作为适配器验收。
- `overwrite` 只属于写盘：plan 回答「写到哪」，不回答「能不能覆盖」。
- 规划的输入仍是 `&[GeneratedFile]`，`table`/`kind` 字段被忽略；等出现第二个导出适配器（如 CLI）再收窄输入类型。
- 已存在文件与符号链接的检查各自需要一次真实文件系统往返，这部分行为无法纯测，只能由集成测试覆盖。
